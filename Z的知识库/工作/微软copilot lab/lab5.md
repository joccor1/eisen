# Lab 5: 使用 Superpowers 开发并验证一个网站

## 实验目标

本实验将使用 [Superpowers](https://github.com/obra/superpowers) 提供的软件开发工作流，从一个初步想法出发，依次完成需求澄清、设计、实施计划、测试驱动开发和最终验证。

完成本实验后，你将能够：

- 理解 Superpowers 的基本理念以及主要 Skill 的职责
- 从 Marketplace 安装并验证 Superpowers
- 使用 `brainstorming` 把模糊想法整理成经过确认的设计
- 使用 `writing-plans` 把设计拆分为可执行、可测试的任务
- 使用 `subagent-driven-development` 调度多个子 Agent 实施计划
- 理解测试驱动开发中的 RED、GREEN、REFACTOR 循环
- 运行并从功能、测试、构建和视觉效果等方面验证网站

---

## 什么是 Superpowers

Superpowers 是一套面向编码 Agent 的可组合 Skill 和软件开发方法。它强调 Agent 不应在收到需求后立即编写代码，而应先理解真正的目标，形成设计并得到用户确认，然后制定足够清晰的实施计划，最后通过测试驱动开发和分阶段审查完成实现。

它的核心理念包括：

- **先设计，后编码**：先澄清需求、比较方案并确认设计
- **计划驱动**：把设计拆分成小而明确的实施任务
- **测试先行**：通过 RED、GREEN、REFACTOR 循环实现功能
- **系统化协作**：为每项任务分配新的子 Agent，并进行规格与代码质量审查
- **以证据为准**：运行测试、构建和实际应用后，才能宣布任务完成

## 步骤 3: 使用 brainstorming 完成设计

在聊天框中输入：

```text
/superpowers:brainstorming 基于 Next.js 创建旅游网站的前端页面，用于浏览全球知名的旅游景点。景点图片使用知名 CDN 的图片
```

`brainstorming` 的目的不是立即创建网站，而是把初始想法逐渐变成可以实施的设计。在这一阶段，Agent 通常会：

- 检查当前项目环境
- 询问受众、页面范围、交互方式和视觉风格等问题
- 提出不同实现方案并说明取舍
- 分段展示设计，等待你的确认或修正
- 保存经过确认的设计文档

认真回答 Agent 每次提出的问题，不要为了尽快进入编码阶段而直接接受所有默认选项。设计完成后，检查以下内容是否已经明确：

- 网站需要哪些页面或主要区域
- 用户如何浏览、筛选或查看景点
- 移动端和桌面端的响应式表现
- 图片 CDN 的选择、来源与失败处理方式
- 技术栈、组件边界以及测试策略
- 哪些功能属于本次范围，哪些暂不实现

只有在理解并认可设计后才批准进入下一阶段。

### 理解 brainstorming 的职责

`brainstorming` 解决的是“应该构建什么、为什么这样构建”，而不是“代码怎么写”。如果设计仍存在歧义，后续计划即使非常详细，也可能精确地实现错误目标。

## 步骤 4: 使用 writing-plans 创建实施计划

确认设计文档后，输入：

```text
/superpowers:writing-plans
```

`writing-plans` 会把已批准的设计转换为一组小而明确的任务。一个可执行的计划通常会包含：

- 要创建或修改的准确文件
- 每个组件或功能的职责
- 先写哪一个失败测试
- 如何确认测试因预期原因失败
- 让测试通过所需的最小实现
- 测试、Lint、构建和提交检查点

阅读生成的计划，不要把“计划文件已生成”等同于“计划一定正确”。重点检查：

- 计划是否覆盖已批准设计中的所有核心要求
- 任务顺序是否允许持续得到可运行、可测试的结果
- 是否明确体现测试先行，而不是先实现、后补测试
- 是否包含响应式布局、可访问性和 CDN 图片加载等验证
- 是否引入了设计中没有要求的额外复杂功能

发现遗漏或过度设计时，先让 Agent 修正计划，再进入实施阶段。

### 理解 writing-plans 的职责

`writing-plans` 解决的是“如何以低风险、可验证的顺序实现设计”。它提供的是实施依据，而不是另一份宽泛的需求说明。

## 步骤 5: 使用 subagent-driven-development 实施计划

确认计划后，输入：

```text
/superpowers:subagent-driven-development 需要使用 test-driven-development，全程使用 Opus 4.8 模型
```

这个阶段会由主 Agent 读取计划并协调实施。典型流程是：

1. 为当前任务派发一个新的实现子 Agent
2. 子 Agent 按照 `test-driven-development` 先编写测试
3. 运行测试，确认它因缺少目标功能而失败（RED）
4. 编写让测试通过的最小实现（GREEN）
5. 在保持测试通过的前提下整理代码（REFACTOR）
6. 由独立子 Agent 先审查规格符合度，再审查代码质量
7. 修复审查问题并重新审查，然后继续下一项任务

运行过程中观察工具调用、测试输出和子 Agent 的审查结果。重点识别以下证据：

- 每个新增行为是否先有失败测试
- RED 阶段的失败是否来自缺少功能，而不是测试代码错误
- GREEN 阶段是否只实现当前测试要求的行为
- 规格审查与代码质量审查是否按顺序进行
- 审查发现的问题是否经过修复和复查
- 所有子 Agent 是否确实使用了 Opus 4.8

如果模型不可用、测试无法正确失败、计划与实际项目冲突或 Agent 报告阻塞，应先处理原因，不要要求 Agent 跳过质量门禁继续生成代码。

### 理解 subagent-driven-development 的职责

`subagent-driven-development` 不是简单地并行生成代码。它通过“每项任务使用新上下文”和“两阶段审查”减少上下文污染、遗漏需求与未经验证的实现。`test-driven-development` 则为每个行为建立可以重复运行的验证证据。

## 步骤 6: 运行并验证网站

全部任务完成后，不要只依赖 Agent 的完成报告。查看项目中定义的 npm scripts，并依次完成适用的验证。

### 自动化验证

至少确认以下检查成功：

- 单元测试和组件测试全部通过
- Lint 与类型检查没有错误
- Next.js 生产构建成功
- 测试输出中没有被忽略的失败、异常或重要警告

常见项目可能使用以下脚本，具体名称以生成项目的 `package.json` 为准：

```text
npm test
npm run lint
npm run build
```

### 运行网站

启动开发服务器：

```text
npm run dev
```

打开终端显示的本地地址，在浏览器中实际操作网站。至少验证：

- 首页能够正常加载，没有控制台错误
- 景点卡片的标题、地点、简介和图片显示正确
- CDN 图片能够加载；加载失败时不会破坏页面结构
- 浏览、筛选、导航或详情交互符合设计
- 页面在窄屏和宽屏下均可使用，没有文字溢出或元素重叠
- 键盘可以访问主要交互元素，文本和背景具有足够对比度
- 刷新页面以及访问主要路由时不会出现 404 或运行时错误

如果发现问题，应先创建能够复现问题的失败测试，再遵循 RED、GREEN、REFACTOR 修复，最后重新运行完整验证。

## 自选主题

本实验使用旅游景点网站作为示例。你可以保留相同流程，将 `brainstorming` 提示词中的主题替换为自己感兴趣的内容，例如：

- 电影或图书浏览网站
- 餐厅与美食发现网站
- 开源项目展示网站
- 摄影作品集
- 课程或活动目录

修改主题时，不要机械保留旅游网站的页面结构。让 `brainstorming` 根据新主题重新澄清受众、核心任务、内容模型和视觉表达。
