# Lab 4: 用 Skill 与 Custom Agent 构建 PPT 创作工作流

## 实验目标

设计一套可以反复迭代的PPT创作流程。完成实验后，你将能够：

- 理解 Skill 与 Custom Agent 在复杂工作流中的不同职责
- 复用仓库已有的 PPT 生成与设计风格能力
- 设计一种文件格式，用来表达演示文稿的分页、内容和视觉意图
- 创建自己的生成 Skill，负责生成和修改这份演示文稿内容文件
- 创建 Review Agent，审查文件并给出可执行的修改意见
- 创建编排型 Custom Agent，将生成、审查、修改和最终 PPT 制作串联起来

## 前置条件

- 已完成前面的 GitHub Copilot、Skill 与 Custom Agent 相关实验
- 能够在 VS Code 中使用 Copilot Chat 的 Agent 模式

---

## 背景

一份质量较高的演示文稿通常要经历内容规划、分页、审查、修改、视觉设计和文件生成等多个阶段。如果让同一个 Agent 在一次对话中同时完成所有工作，内容问题可能直到 PPT 生成后才被发现，修改成本也会变高。

本实验要求你把“内容文件”作为生成流程中的中间产物：先把每一页要表达什么设计清楚，通过审查后，再生成最终的 `.pptx` 文件。

你要构建的流程大致如下：

```text
用户需求
   ↓
生成 Skill 创建内容文件
   ↓
Review Agent 审查分页与内容
   ↓
是否需要修改？ ── 是 ──→ 生成 Skill 根据意见更新文件
   │                         ↑
   └─────────────── 否 ─────┘
   ↓
复用已有 Skill 选择设计风格并生成 PPT
```

> 💡 **关键点**：你创建的生成 Skill 首先负责生成“描述 PPT 的文件”，而不是直接生成 `.pptx`；Review Agent 审查的也主要是这份文件中的分页、内容与叙事结构。

---

## 挑战 1: 理解已有 Skill

仓库的 `.github/skills` 目录已经提供了两个可以复用的 Skill：

- `pptx`：提供创建、编辑和验证 PowerPoint 文件的工作方法与工具
- `design-styles`：提供多种可参考的视觉风格、配色、排版与设计原则

先让 GitHub Copilot 协助你阅读并理解这两个 Skill。重点思考：

- 两个 Skill 分别解决 PPT 创作流程中的什么问题？
- 哪些能力可以直接复用，哪些能力仍然缺失？
- 为什么内容规划和内容审查不应该完全交给最终的 PPT 生成阶段？

不要修改已有 Skill。你的任务是在它们之上补齐内容生成、内容审查和流程编排能力。

---

## 挑战 2: 设计演示文稿内容文件

选择一种你认为适合协作与审查的文件格式，用它记录 PPT 的分页和具体内容。Markdown、JSON、YAML 或其他文本格式都可以，关键在于它是否能清晰表达你的设计意图。

你的文件至少需要让后续 Agent 理解：

- 演示文稿的主题、目标和受众
- 每一页的作用以及页面之间的叙事关系
- 每一页的标题、核心观点和支撑内容
- 哪些内容适合使用图表、图片、数字或其他视觉元素
- 对设计风格、演讲备注或信息来源的必要说明

自行决定文件结构和字段，不必追求复杂。请思考：这种格式是否便于人阅读、便于 Agent 修改，也便于 Review Agent 指出具体页面的问题？

---

## 挑战 3: 创建内容生成 Skill

创建一个属于你的 Skill，用于根据用户提供的主题、受众、目的和其他约束，生成或修改上一步设计的内容文件。

这个 Skill 应该关注内容规划，而不是直接处理 PowerPoint 排版。它需要能够：

- 把较宽泛的需求组织成有起承转合的演示结构
- 决定如何分页，并让每一页只承担清晰的沟通任务
- 按照你定义的格式写入内容文件
- 接收 Review Agent 的意见，并对指定页面或整体结构进行修改
- 避免在修改时破坏已经通过审查的内容

由你决定 Skill 的名称、输入输出约定，以及是否需要附带模板或参考文件。

---

## 挑战 4: 创建 Review Agent

创建一个专门审查演示文稿内容文件的 Custom Agent。它不负责美化 PPT，也不应该在审查时直接替生成 Skill 重写整份文件。

你可以让 Review Agent 从以下角度提出问题：

- 分页是否合理，是否存在一页内容过多或页面过于零散的情况
- 开场、主体和结尾能否形成连贯叙事
- 每页标题是否表达观点，而不只是宽泛的主题标签
- 内容是否符合目标受众和演示目的
- 观点是否有足够的事实、案例或数据支撑
- 是否存在重复、矛盾、跳跃、空洞表述或缺少来源的内容
- 建议的图表或视觉元素是否真正帮助表达信息

审查意见应能够定位到具体页面，并说明问题、原因和期望的修改方向。你还需要为“审查通过”定义一个明确标准，使编排 Agent 知道何时可以进入 PPT 生成阶段。

---

## 挑战 5: 创建编排型 Custom Agent

创建一个 Custom Agent，把整个流程组织起来。它应当协调其他能力，而不是把所有规则重新复制到自己的定义中。

你的编排 Agent 需要能够完成以下闭环：

1. 理解用户的 PPT 需求和成功标准
2. 调用你创建的生成 Skill，产出演示文稿内容文件
3. 将该文件交给 Review Agent 审查
4. 如果未通过，将审查意见反馈给生成 Skill 修改文件
5. 重复审查与修改，直到达到通过标准
6. 再复用 `design-styles` 与 `pptx` Skill 生成并检查最终 PPT

请为循环设置合理边界，并考虑以下情况：审查意见互相冲突、修改后引入新问题、缺少必要事实，以及多轮修改后仍无法通过。此时 Agent 应该继续猜测，还是向用户说明阻塞原因？

---

## 自选演示主题

选择一个你熟悉、同时具有明确受众和沟通目的的主题来验证工作流，例如项目提案、技术方案介绍、产品发布、课程分享或阶段复盘。

不要只测试“能否生成文件”。在运行过程中观察：

- 首次生成的分页有哪些不足？
- Review Agent 是否发现了具体且真实的问题？
- 生成 Skill 能否准确应用审查意见，而不是无关地重写内容？
- 最终 PPT 是否忠实反映了通过审查的内容文件？
- 更换主题后，这套流程是否仍然可复用？

---

## 验收标准

完成实验时，你的成果应满足以下条件：

- 有一份结构明确、可被 Agent 读写的演示文稿内容文件
- 有一个生成或更新该文件的自定义 Skill
- 有一个审查该文件分页、内容和叙事质量的 Review Agent
- 有一个能够驱动“生成—审查—修改—再审查”循环的编排型 Custom Agent
- 只有内容文件通过审查后，流程才会进入 PPT 生成阶段
- 最终生成一份能够正常打开、内容与审查结果一致的 `.pptx` 文件
- 保留至少一轮审查意见和修改结果，用于说明工作流确实发生了迭代
